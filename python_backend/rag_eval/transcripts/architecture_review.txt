Architecture review - notifications service

The architects decided to adopt an event-driven design using Kafka for the notifications service, moving away from the current polling-based approach. The main driver was that polling was causing noticeable delivery delays under load, and an event-driven pipeline should get delivery latency down to under a second. The group rejected a proposal to move the service to gRPC for now, deciding the added complexity wasn't justified until the Kafka migration is stable. Sam will write an architecture decision record documenting the Kafka choice and the gRPC rejection, including the tradeoffs discussed, by end of week. The team also agreed that the migration should happen behind a feature flag so it can be rolled back quickly if delivery guarantees regress. There was strong agreement in the room that this was the right technical direction, though a few people flagged operational complexity -- running Kafka reliably -- as the main risk to watch. To manage that risk, the group decided to start with a managed Kafka offering rather than self-hosting, at least for the first two quarters, and revisit self-hosting once the team has more operational experience with the platform. Sam will include that phasing in the ADR as well. The team also agreed to set up a dedicated dashboard for consumer lag and delivery latency before the migration goes live, so any regression is visible immediately rather than discovered through customer complaints. Priya volunteered to help Sam scope the dashboard requirements early next week.
